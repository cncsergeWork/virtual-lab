# Virtual Lab — продолжение разработки

Актуально на 26.11.2026. Это локальное приложение Windows x64 на C++20 и Qt Quick. Пользователь собирает операторские экраны мышкой, привязывает элементы к тегам, получает телеметрию и просматривает историю. Переносимая сборка находится в `dist/Virtual-Lab`. Разговор с пользователем ведётся на русском языке.

## Продолжение в новом чате

Откройте корневую папку SCADA как проект Codex и создайте новый чат в этой же папке. Новый чат получает контекст из файлов проекта. Начальное сообщение может быть таким.

> Продолжаем разработку Virtual Lab в этой папке. Прочитай AGENTS.md и HANDOFF.md, сверь текущее состояние с кодом и выполни следующую задачу.

Текущее состояние в коде включает локальный редактор, Modbus TCP, приём JSON-телеметрии v1, архив SQLite, сводные и раздельные графики, настраиваемый многорядный тренд, приборы Qt Quick и условное оформление виджетов. Для проверки на реальном стенде остаётся подтверждение физического подключения источника телеметрии, особенно USB COM.

## Что переносить

- Для запуска достаточно целиком скопировать папку актуальной сборки и открыть `Virtual-Lab.exe`.
- Для продолжения разработки нужны `src/`, `qml/`, `tests/`, `assets/`, `CMakeLists.txt`, `build.ps1`, `engine-tags.json`, `README.md`, `AGENTS.md`, `QA.md`, `LICENSE`, `LICENSES/` и этот файл. Папку `build/` заново создаёт CMake. `.toolchain/` можно заново подготовить на другой машине.
- Пользовательские проекты хранятся отдельно. Переносите вместе `*.scada.json`, `history.sqlite` и `images/`. Перед копированием базы закройте приложение. UUID проекта и тегов связывают конфигурацию с архивом.

## Сборка и тесты

Рабочая конфигурация использует Qt 6.8.3 x64 MinGW, MinGW 13.1, CMake и Ninja. Qt-модули включают Qt Quick, Qt Quick Controls, Qt Network, Qt Serial Bus, Qt Serial Port, Qt WebSockets, Qt SQL с SQLite и Qt SVG. Переносимая сборка включает `Qt6Svg.dll` и `imageformats/qsvg.dll`. Для установленного отдельно Qt укажите `-QtRoot` и `-CompilerBin` при запуске скрипта.

```powershell
.\build.ps1
.\build.ps1 -Deploy
```

Если инструментов нет, на Windows можно подготовить локальный комплект через Python 3 и `aqtinstall`. Команды выполняются из корня проекта.

```powershell
py -3 -m venv .toolchain\venv
.\.toolchain\venv\Scripts\python.exe -m pip install aqtinstall cmake ninja
.\.toolchain\venv\Scripts\aqt.exe install-qt windows desktop 6.8.3 win64_mingw -O .toolchain\Qt --archives qtbase qtdeclarative qtshadertools qtsvg -m qtserialbus qtserialport qtwebsockets
.\.toolchain\venv\Scripts\aqt.exe install-tool windows desktop tools_mingw1310 qt.tools.win64_mingw1310 -O .toolchain\Qt
```

CTest запускает тесты ядра, основной сценарий QML через `--ui-test` и проверку кнопок и файлов через `--ui-audit`. Сценарии работают с временными проектами и отдельными настройками. Интеграционные тесты используют TCP-сокеты `127.0.0.1`. Интерфейсные тесты используют порт 15020 по очереди. Для снимков интерфейса задайте `SCADA_UI_CAPTURE` абсолютным путём к существующей папке. Таблица проверенных действий и границы прогона описаны в [QA.md](QA.md).

В Windows CTest передаёт интерфейсным тестам путь к системным шрифтам для режима `offscreen`, если `QT_QPA_FONTDIR` не задан при конфигурации CMake.

Исходник иконки — `assets/virtual-lab.svg`. При изменении рисунка обновите также `assets/virtual-lab.ico` с кадрами от 16 до 256 px. Ресурс `assets/virtual-lab.rc` встраивает ICO в Windows EXE, `src/main.cpp` использует его для окон Qt, верхняя панель рисует SVG.

Свойство `Studio::alarms` обновляется по отдельному сигналу `Runtime::alarmsChanged` при изменении состава или квитирования тревог. Это сохраняет нажатие кнопки в журнале во время обновлений телеметрии. Проверку с удержанием кнопки до очередного показания выполняет `--ui-audit`.

## Навигация и рабочая область

Видимое название берётся из `QGuiApplication::applicationDisplayName` в `src/main.cpp`. Для QSettings используются прежние внутренние идентификаторы приложения и организации, поэтому настройки редактора доступны после переименования.

Верхняя полоса в `qml/Main.qml` объединяет меню проекта, вкладки и управление опросом. В операторском режиме мнемосхема начинается под компактной полосой экранов. При одном экране эта полоса скрывается. Длинный список экранов прокручивается горизонтально.

В редакторе потяните за правый край левой панели или за левый край панели свойств. `qml/Dashboard.qml` сохраняет ширину каждой панели при отпускании мыши в отдельных пользовательских настройках Qt (`editor/paletteWidth` и `editor/inspectorWidth`). В узком окне видимая ширина ограничивается доступным местом для холста, значения в настройках сохраняются. Переносимый комплект Qt включает модуль `QtCore` для QML.

Кнопки **Палитра** и **Свойства** в полосе редактора отдельно скрывают и показывают боковые панели. Холст занимает освободившееся место. Состояние каждой панели восстанавливается при запуске из пользовательских настроек Qt (`editor/paletteCollapsed` и `editor/inspectorCollapsed`). При разворачивании применяется сохранённая ширина.

**F11** открывает полноэкранный операторский режим. **Esc** или повторное **F11** возвращает предыдущую вкладку и оконное состояние. Для смены экранов во время работы на всю область используются виджеты **Переход**. С **Обзора станции** есть переход на экран **Все элементы**.

В редакторе **Экран → Свойства экрана…** открывает название, размер, фон и шаг сетки. Смену размера можно применить с пропорциональным переносом координат относительно ширины и высоты или с сохранением текущих размеров элементов там, где они помещаются. Для фонового изображения используются те же файлы `images/`, что и для виджетов. В режиме **Сохранить как** изображения копируются в папку нового проекта.

Формат проекта версии 1 поддерживает необязательные `screen.width`, `screen.height`, `screen.background`, `screen.backgroundImage`, `screen.backgroundFit`, `screen.gridStep` и `screen.operatorFit`. Старые экраны открываются с областью 1200 × 692 и сеткой 10 px. Размер исходной области также сохраняется в новых шаблонах.

По умолчанию в операторском режиме и по F11 мнемосхема заполняет доступную область. `qml/Dashboard.qml` перераспределяет координаты и размеры ячеек по ширине и высоте. Отрисовка шрифтов и круглых приборов использует единый масштаб. В свойствах экрана можно выбрать **Сохранять пропорции экрана** (`operatorFit: "fit"`), чтобы сохранить расположение и пропорции всей композиции с полями.

Демопроект из `src/demo.cpp` содержит шесть экранов, включая **Все элементы** со всеми 26 базовыми виджетами из палитры, рабочий пульт **Управление**, экран **Типовые панели** и пример **Свой насос**. Картинка контура берётся из встроенного ресурса `assets/demo-loop.png` и доступна в открытом и сохранённом демопроекте.

## Конструктор своих виджетов

**Свои виджеты → Создать виджет…** открывает диалог с именем и размером, затем пустой холст. Конструктор сохраняет тип в `faceplates`, использует прежние интерфейсные теги, опубликованные свойства экземпляра, импорт и экспорт `*.faceplate.json`. Иконки и фон можно делать из изображений PNG, SVG, JPEG и BMP и фигур. Картинки копируются в `images/`. До первого сохранения они лежат во временной папке приложения. Экспорт читает изображения из папки проекта, временной папки и перечисленных в `Project::isDemoImage` встроенных ресурсов.

`qml/WidgetLayers.qml` перечисляет слои от верхнего к нижнему. Порядок отрисовки задаётся порядком элементов в JSON-массиве `items`. Флаг `item.locked` защищает координаты и размеры при перетаскивании и выравнивании. Необязательный `item.visible` задаёт начальную видимость. В `item.appearance.rules` к цветам добавлены результаты `visible` и `text`. В операторе динамическая привязка опубликованной видимости экземпляра приоритетнее правила, затем используется начальная видимость слоя. Редактор оставляет скрытые слои доступными для выбора. Изображения загружаются заранее, чтобы смена видимости не сбрасывала картинку.

Фигуры имеют `kind: "shape"` и свойство `shape` со значением `rectangle`, `ellipse` или `line`. Прозрачная зона команды хранится как `kind: "hitArea"` и использует обычные действия. Фигуры и зоны команды поддерживают размер от 8 × 8 px. `WidgetPreview.qml` показывает тот же `ScreenItem.qml` с локальной таблицей пробных значений. Пробные записи обновляют только эту таблицу, а команды чтения и записи отображаются в журнале предпросмотра. Переходы между экранами в пробном режиме отключены.

Настройки **Анимация слоя…** в `qml/LayerAnimationDialog.qml` хранятся в необязательном `item.animation`. Поля `kind` (`rotate` или `blink`), `tag`, `op`, `limit`, `periodMs` обязательны для настроенного эффекта. Для диапазонов есть `max`, для вращения — `reverse`, для мигания — `dimPercent`. Тег интерфейса преобразуется в тег экземпляра тем же путём, что и теги других свойств. После удаления привязки эффект сохраняется, а поле тега очищается. Слой запускает эффект в операторе и в **Предпросмотре** при выполнении условия и хорошем качестве сигнала. Вращение идёт вокруг центра слоя. По завершении условия угол и непрозрачность возвращаются к исходным значениям.

В демопроекте откройте **Свой насос**, затем дважды щёлкните экземпляр в редакторе, чтобы открыть тип **Насос · конструктор**. Корпус, зелёная накладка и крыльчатка хранятся в трёх встроенных SVG. В предпросмотре включите пробное состояние **Насос работает**, чтобы увидеть вращение крыльчатки, и введите уровень 65 %, чтобы увидеть мигание плашки **Высокий уровень**. В операторском режиме команды работают на встроенном симуляторе. Крыльчатка вращается при подтверждённом сигнале работы, а плашка появляется и мигает при уровне от 60 %.

## Лицевые панели

Кнопка **Создать виджет…** в палитре открывает диалог с фокусом в поле **Название типа**. **Создать** или **Enter** открывает пустой холст заданного размера. Интерфейсный тест проверяет этот путь щелчком по кнопке, вводом названия и нажатием Enter.

В раскрывающемся списке **Свои виджеты** у каждого типа есть действия **Дублировать**, **Переименовать** и **Удалить**. Дублирование открывает диалог со свободным именем с суффиксом **(копия)** или **(копия 2)**. Пользователь может ввести своё имя. После подтверждения Virtual Lab открывает холст копии, сохраняет её макет и настройки, создаёт новые UUID типа, элементов, групп, интерфейсных тегов и опубликованных свойств и перенаправляет внутренние ссылки. Экранные экземпляры и шаблоны остаются связаны со своими типами. Переименование сохраняет UUID. Удаление требует подтверждения и доступно после удаления всех экранных экземпляров и шаблонов, которые ссылаются на тип. При отказе приложение указывает первую найденную ссылку.

Выделите размещённый фейсплейс и выберите в инспекторе **Сменить тип…**. Таблица показывает используемые поля выбранного экземпляра, автоматически подставляет совпадения и позволяет их изменить. `Studio::changeFaceplateType` принимает необязательную карту UUID старого поля → UUID поля выбранного типа. Привязки, `overrides` и `propertyBindings` переносятся одной операцией с отменой. ID, положение, размеры и подпись экземпляра сохраняются. Компонент `qml/FaceplateFieldMapping.qml` и проверка сопоставлений используются также для замены при импорте.

Подтверждённые сопоставления при смене типа сохраняются вместе с проектом в необязательном объекте `faceplateMappings`. Ключи задают исходный тип, новый тип и старое поле, а значение содержит UUID нового поля. Запись обновляет только подтверждённые строки и входит в ту же операцию отмены. Диалог учитывает совместимость сохранённого выбора. Для обратного направления без своей настройки используется однозначное обратное соответствие. Удаление типа удаляет связанные пары, а удалённые или несовместимые поля нужно выбрать снова. Формат файла отдельного типа остаётся прежним.

Дубликаты сохраняют необязательное поле `originId` у типа, интерфейсных тегов и свойств. Оно хранит UUID исходного поля или типа и сохраняется при редактировании имён. У родственных типов автоматический выбор использует `originId` или собственный UUID исходного поля. Для старых копий и других типов выбор выполняется по имени без учёта регистра. При ручном выборе должны совпадать тип тега или вид свойства. Если для использованного поля нет уникального совместимого назначения, смена блокируется. Удаление исходного типа после перехода экземпляров сохраняет возможность сопоставлять его копии по оставшимся `originId`.

Кнопка **Создать копию типа…** в инспекторе открывает диалог с предложенным свободным именем. После подтверждения `Studio::duplicateFaceplateForInstance` создаёт именованный тип, переносит настройки экземпляра одним изменением проекта и открывает редактор копии через экземпляр. Кнопка **← На экран** возвращает к этому же экземпляру. Одна команда отмены возвращает ему прежний тип и убирает копию из списка.

Действие **Экспорт…** в строке типа сохраняет файл `*.faceplate.json`. После выбора файла через **Импорт…** можно создать тип под предложенным или своим свободным именем либо заменить существующий тип. Импорт открывает холст получившегося типа. Контейнер `scada-faceplate` версии 1 хранит определение в `faceplate`, картинки в объекте `images` в Base64 и имена экранов назначения в `screens`. При импорте внутренние UUID обновляются тем же способом, что при дублировании. Если имя в файле занято, диалог предлагает свободный суффикс **(копия)**. Переходы связываются по ID экрана или совпадающему имени. О переходах без подходящего экрана сообщает редактор, их экран задаётся в свойствах виджета. Теги проекта назначаются экземплярам в проекте назначения.

При замене сохраняются UUID и имя типа в проекте назначения. Для всех экземпляров на экранах и в шаблонах `Studio::importFaceplate` использует тот же перенос привязок, переопределений и правил по тегам, что при смене типа. Несовместимость используемого поля прерывает операцию до записи изображений и изменения проекта. Новое определение и перенесённые настройки отменяются одной командой. Тест `faceplateImportReplacement` проверяет замену родственного типа и типа из отдельного проекта с совпадающими именами полей, перенос на несколько экранов и в шаблон, отмену и отказ при несовместимости.

После выбора типа для замены диалог показывает использованные поля со всех экранов и шаблонов. Совпадения заполняются автоматически по UUID происхождения у родственных типов и по имени у остальных. Пользователь может изменить любое предложенное сопоставление. Для каждого поля доступны теги того же типа или свойства того же вида. `Studio::importFaceplate` принимает необязательную карту UUID старого поля → UUID поля в файле и проверяет полноту, совместимость и уникальность назначений до изменения проекта. Файл типа сохраняет прежний формат.

Подтверждённые сопоставления импорта хранятся вместе с проектом в `faceplateImportMappings`: UUID заменяемого типа → UUID происхождения типа из файла → UUID текущего поля → UUID происхождения поля из файла. При успешной замене приложение переводит сохранённые записи на новые локальные UUID и сохраняет соответствие с прежним исходным типом, если у него другое происхождение. Сопоставления учитываются повторно после открытия проекта, в том числе для файлов, заново экспортированных с другими UUID полей. Удалённое или несовместимое поле нужно выбрать снова. Удаление заменяемого типа удаляет его записи. Формат `*.faceplate.json` остаётся прежним.

Изображения распаковываются в `images/` с новыми именами. Для ещё не сохранённого проекта используется временная папка приложения. При первом сохранении файлы переносятся в папку проекта, в том числе файлы, которые понадобятся при повторе отменённого импорта. Тест `faceplateTransfer` проверяет экспорт с картинкой, перенос в новый проект, два варианта привязки переходов, повторный импорт и отказ при повреждённом пакете.

Лицевая панель использует модель типа и экземпляра. Тип редактируется на отдельном холсте и хранится один раз. Экземпляр можно перемещать и растягивать как обычный виджет. Его размеры задают масштаб дочерних элементов, а их координаты остаются локальными для типа. Все экземпляры используют текущую редакцию типа. На экране **Типовые панели** два экземпляра одного типа показывают значения разных тегов.

В формате проекта версии 1 типы хранятся в необязательном массиве `faceplates`. У типа есть `id`, `name`, целые `width` и `height` от 80 × 52 до 8192 × 8192, массив `ports` и обычный массив элементов `items`. У каждого интерфейсного тега есть `id`, `name` и `type` (`number`, `bool` или `text`). Экранный элемент с `kind: "faceplate"` ссылается на тип полем `faceplate`. Его необязательный объект `bindings` хранит соответствия UUID интерфейсных тегов UUID тегов проекта. Для непривязанного тега ключ можно пропустить или оставить пустую строку. Вставка из библиотеки типов создаёт отдельный экземпляр.

Поля тегов внутри типа используют UUID его интерфейса. Сюда входят обычное показание, обратная связь, ряды тренда, условия оформления и источники и назначения событий. В операторском режиме ссылки разрешаются в теги проекта отдельно для каждого экземпляра, а события дочерних элементов получают идентификаторы с учётом экземпляра. Ссылка на экран в дочернем элементе `link` разрешается в пределах проекта. Внутри типа используются обычные виджеты. В шаблонах можно сохранить экземпляр панели с непривязанным интерфейсом.

В **Интерфейс свойств…** редактора типа добавляются свойства конкретных дочерних виджетов. **Свойства экземпляра…** в инспекторе задают их значения для выбранного экземпляра. В типе можно сохранить до 128 строк в необязательном массиве `properties`. У каждой есть UUID `id`, уникальное в типе имя `name` длиной до 80 символов, UUID дочернего `item` и `kind` (`title`, `captionColor`, `background`, `value` или `visible`). Для одного элемента каждый вид свойства публикуется один раз. У `visible` есть необязательный логический `defaultVisible` со значением `true` по умолчанию.

Экземпляр хранит переопределения в необязательном объекте `overrides`. Ключом служит UUID свойства, значением служит строка для подписи, цвет `#RRGGBB` или логическое значение для видимости. Отсутствующий ключ наследует значение типа. Явно заданные пустая подпись и `false` сохраняются. Удаление свойства или дочернего элемента очищает соответствующие переопределения. Шаблоны сохраняют оформление экземпляра. При вычислении цвета совпавшие правила по порогам применяются поверх базовых `background` и `value`.

Кнопка **По тегу…** в свойствах экземпляра добавляет одно условие для каждого опубликованного цвета или видимости. Параметры сохраняются в необязательном объекте `item.propertyBindings` с ключами UUID свойств. Правило хранит `tag` (UUID числового или логического тега проекта), `op` (`alarm`, `lt`, `lte`, `eq`, `ne`, `gte`, `gt`, `between`, `outside`), `value` при выполнении условия и необязательное `otherwise` в остальных случаях. Для числовых операций нужны конечный `limit` и конечный `max` у диапазонов. Границы входят в диапазон. Результаты имеют формат `#RRGGBB` для цвета и `true` или `false` для видимости.

В операторском режиме `Project::faceplatePropertyValues` принимает правила дочернего виджета с ключами по виду свойства. Совпавшая ветвь заменяет соответствующий цвет или видимость поверх обычного оформления, включая правила виджета по порогам. Числовое сравнение выполняется по конечному показанию с хорошим качеством. При недоступном показании, пустом `tag` или отсутствии результата для выбранной ветви действует обычное оформление. Операция `alarm` проверяет присутствие тега среди активных тревог, включая квитированные тревоги и тревоги при устаревшем показании. Сохранение шаблона и удаление тега очищают `tag`, оставляя условие и результаты. Удаление свойства или смена его вида очищает соответствующее правило на экранах и в шаблонах.

В демопроекте плашка насоса **АВАРИЯ** связана с тревогой тега **Уровень бака**. Интерфейсный тест связывает такую же плашку у клапана с отдельным дискретным тегом, переключает его через симулятор и проверяет появление, свой цвет и скрытие. Тест ядра `faceplatePropertyBindings` проверяет пороги, качество показаний, сохранение и очистку привязок.

## Элементы управления и мнемосхемы

Кнопка `command` и элементы `switch`, `valve`, `setpoint`, `slider`, `knob` и `selector` поддерживают настройку **События и действия…**. Проект хранит до 32 строк в необязательном массиве `item.actions`. У строки есть `event` (`press`, `release`, `click`, для числовых виджетов также `change`), `action` (`write` или `read`) и `tag`. Для записи добавляется `valueMode` (`widget`, `constant` с числовым `value` или `tag` со ссылкой `valueTag`). В последнем случае `tag` остаётся тегом назначения, а `valueTag` может ссылаться на числовой или логический тег другого источника. Сохранение шаблона и удаление тега очищают соответствующую ссылку. Пустой список использует встроенную команду. Прежнее поле `confirmWrite` допускается при загрузке для совместимости.

Для ползунка и поворотной ручки `press` и `release` относятся к самому контролу, а `click` к кнопке **Записать**. У числового поля `press`, `release` и `click` относятся к кнопке **Записать**. Событие `change` передаёт завершённое изменение значения. Показания привязаны к обычным тегам чтения и обратной связи. `Studio::runWidgetActions` передаёт настроенные действия в `Runtime::runWidgetActions`. Действия одного виджета сохраняют порядок, пока чтение тега-источника ожидает ответа. Встроенная команда вызывает `Studio::write`. Перед записью применяется проверка доступа в `Runtime::requestWrite`.

Действие чтения запрашивает один тег Modbus TCP. Ответ обновляет обычное показание этого тега. Режим **Из другого тега** запрашивает свежее показание Modbus и записывает значение из успешного ответа. Для потоковой JSON-телеметрии берётся последнее актуальное показание с хорошим качеством. При рабочей связи чтения и записи в пределах источника выполняются по одной до ответа и сохраняют порядок общей очереди. При остановке, разрыве связи или неясном исходе операции ожидающие действия отменяются. Восстановившееся соединение начинает работу с пустой очередью. Результаты чтения доступны в журнале.

`switch` и `valve` принимают логический тег и необязательную ссылку `feedback` на логический тег фактического положения. Удаление тега и сохранение шаблона освобождают эту привязку. Числовые регуляторы используют `min`, `max`, `decimals` и необязательный положительный `step`, ограниченный диапазоном. По умолчанию шаг учитывает масштаб целочисленного тега либо долю диапазона для Float32. Виджет `selector` хранит необязательный массив `positions` из 2–6 объектов с `label` и уникальным числовым `value`.

`pipe` рисует отрезок в направлении из свойства `vertical` и окрашивает его по состоянию тега. Отрезки стыкуются размещением на холсте. `motor` показывает состояние двигателя, `bargraph` использует те же свойства шкалы и цветов, что и приборы. `alarm` выводит активную тревогу выбранного тега или последнюю активную тревогу проекта при отсутствии привязки. Квитирование использует существующий журнал.

Симулятор хранит команду клапана в Coils по адресу 1, обратную связь в Discrete Inputs по адресу 1 и режим насоса в Holding Registers по адресу 1. Режимы 0, 1 и 2 означают останов, ручное задание и автоматическую поправку по уровню. Интерфейсный тест проверяет встроенные команды, действия по событиям, обратное чтение, диапазон и квитирование.

## График операторского экрана

Добавьте **Тренд** в редакторе и откройте **Ряды, шкалы и период…**. Настраиваются теги, цвет и вид каждого ряда, период по умолчанию, подписи времени, легенда и меню периода. Общая шкала сопоставляет однородные сигналы. Двухосевая шкала группирует ряды слева и справа. В независимом режиме у каждого ряда своя цветная ось в единицах тега с настраиваемой стороной, делениями и фиксированным либо автоматическим диапазоном. Если места для всех подписей мало, виджет оставляет часть осей по порядку рядов, а линии сохраняют собственные диапазоны. Отдельный архив по-прежнему предлагает нормализацию 0–100% в сводном виде.

Подпись периода в шапке и правая кнопка на графике открывают меню с переходом к текущему времени, всему архиву и выбором интервала. Легенда управляет видимостью рядов. Текущее или выбранное курсором значение видно при наведении на легенду либо постоянно, если это включено в свойствах. Колесо масштабирует время, перетаскивание сдвигает его, щелчок закрепляет курсор. Графики используют архивные значения и прерывают линию при разрыве связи. В демопроекте виджет показывает уровень, давление и обороты на трёх шкалах.

Формат проекта остаётся версии 1. Для старого поля `item.tag` есть однорядный режим. Виджет хранит объект `item.trend` с `seconds`, `axis` (`shared`, `dual` или `individual`), `legend`, `toolbar` (доступность меню периода) и массивом `series`. Необязательный `timeLabels` принимает `auto` (относительное время в скользящем окне, часы в истории), `relative` (секунды от правого края) либо `clock` (время записи). Необязательный `legendValues` включает значения в легенде. Ряд содержит `tag`, `color`, `side`, `style` и необязательные `min`, `max` и `divisions` (число делений от 2 до 12). Сохранение шаблона освобождает UUID привязок, а удаление тега очищает его привязки на экранах.

## Цвета и пороги виджетов

Выберите элемент и откройте **Цвета и пороги…**. Можно задать основные цвета фона и показания, а также до 32 правил. Источником условия служит тег самого элемента, первый привязанный ряд тренда или явно выбранный числовой либо логический тег. Для проверки оформления в диалоге можно ввести пробное значение. На демоэкране **Обзор станции** карточка давления зелёная от 2 бар и янтарная ниже 1 бар.

Проверка идёт сверху вниз. Первое совпавшее правило заменяет только заданные в нём цвета. При отсутствии достоверного значения видны основные цвета и сохраняется индикация качества. Эти условия управляют внешним видом. Пороговые тревоги настраиваются в теге отдельно. Цвета отдельных линий графика задаются в настройках рядов.

Параметры сохраняются в необязательном `item.appearance`. В нём могут быть `background` и `value` в формате `#RRGGBB`, UUID `tag` для условий и массив `rules`. У правила есть `op`, `limit`, один или оба цвета и верхняя граница `max` у диапазонов. Допустимые операции `lt`, `lte`, `eq`, `ne`, `gte`, `gt`, `between`, `outside`. Границы диапазона включены. Удаление тега или создание шаблона очищает отдельную ссылку на тег, сохраняя правила.

## JSON-телеметрия v1

Исходный контракт находится в `html/PROTOCOL.md` соседнего репозитория стенда. Поведение клиента описано в `html/service/server.py`, преобразования панели — в `html/engine-core.js`.

Источник `engine-json` принимает поток напрямую от ESP. В JSON сохранённых проектов используется этот идентификатор драйвера. Пример WebSocket-адреса `ws://192.168.4.1:81/ws`. USB COM использует 115200, 8N1 и ответы `@JSON\n`. Драйвер посылает `hello` с клиентом `engine-local-monitor`, ждёт `identity` версии 1, затем принимает полные пакеты `telemetry` версии 1 с `session`, `ts` и `values`. `ts` служит для фильтрации повторов в пределах загрузочной сессии. Для шкалы времени архив использует часы компьютера при получении пакета. При отсутствии поля, `null` или тайм-ауте старое число не превращается в ноль.

В **Источники → + Источник → JSON-телеметрия** выбирайте WebSocket или USB COM. Пример тегов можно загрузить галочкой при создании источника или через меню **Теги JSON**. Файл примера находится в `engine-tags.json`. То же меню импортирует и экспортирует таблицы выбранного подключения. Путь записывается через точки, например `values.rpm` или `state`. Числа и логические значения архивируются и рисуются. Текстовые статусы доступны в списке тегов и виджете значения. Преобразование чисел следует формуле `сырой сигнал × scale + bias`. Например, для перевода импульсов в л/мин применяется `мл на импульс / 1000` как масштаб.

Подключение работает в режиме мониторинга и отправляет только приветствие. Для приёмки на стенде нужно проверить фактический URL или COM-порт, версию прошивки и имена полей. Тестовый WebSocket и разбор COM-кадров проверяются автоматически.
